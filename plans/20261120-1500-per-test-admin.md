# 2026-11-20 15:00 UTC — Per-test admin instead of the shared pre-seeded admin

## TL;DR

**Why:** System tests create a fresh customer per test (`newCustomer` → `IdentityProviderDriver.createCustomer`), but every admin test signs in as one shared, pre-seeded admin (`UserIdentity.ADMIN`, `loggedInAsAdmin()`). That breaks test isolation: parallel tests sign in with the same account at once (the reason brute-force detection is off in the test realms, `docs/operations/edge-rate-limiting.md`), any change to the admin account leaks into other tests, and every environment's realm has to pre-seed that user.
**End result:** Admin tests create their own admin, the same way they create a customer (`newAdmin`, mirroring `newCustomer`), in Java, .NET and TypeScript. The shared `UserIdentity.ADMIN` and the pre-seeded test admin are gone from the system tests.
**Unchanged:** production realm, the app's role checks (`SecurityConfig` ADMIN/CUSTOMER), brute-force settings in prod. Whether test realms can turn brute-force detection back on is a follow-up, not part of this plan.

Origin: substack article "Core Use Case Narrative & Business Rules in Legacy Code with AI" lists "Create Admin" as a setup dependency of Publish Coupon; the shop does not do this yet.

## Items

1. **Driver:** add `createAdmin(...)` to the identity provider driver port and the Keycloak adapter (create the user and assign the realm `ADMIN` role), in all three languages (`system-test/java`, `system-test/dotnet` `KeycloakAdminClient.cs`, `system-test/typescript`).
2. **DSL:** add `newAdmin(...)` to `UseCaseDsl` next to `newCustomer`, plus a `UserIdentity.admin(account)` factory. Make `loggedInAsAdmin()` (Java `GivenImpl`, TS `given-stage.ts` / `arrange-given.ts`, .NET equivalent) create a fresh admin per scenario instead of returning the shared `UserIdentity.ADMIN`.
3. **Tests:** migrate every use of `UserIdentity.ADMIN` / `loggedInAsAdmin()` (e.g. `BrowseCouponsPositiveIsolatedTest`, `BrowseCustomersPositiveTest`, `DeliverOrder*Test`, `ThenCouponImpl`, `app-context.ts`, `then-checkout.ts`) and their .NET/TS twins. Check any assertion that relies on "the" admin (e.g. coupons published by the admin).
4. **Realms:** remove the pre-seeded test admin from the local / acceptance / QA realm imports once nothing references it (keep whatever admin the stage deploys need for non-test use).
5. **Verify:** compile all three languages, run the admin-touching acceptance tests in parallel, then the full `test-all` run (Lane D rules from the meta-plan).
6. **Follow-up idea for REL:** with no shared users left, evaluate re-enabling brute-force detection in the test realms (also needs per-test customers everywhere, `UserIdentity.customer(index)` is still shared).
