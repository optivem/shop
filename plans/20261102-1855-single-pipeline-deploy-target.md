# 2026-11-02 18:55:09 UTC — Single release owner: cloud acceptance + Docker gates

## TL;DR

**Why:** Each of the six flavors has two parallel sets of acceptance, QA and prod workflows: Docker (`*-acceptance-stage`, `*-qa-stage`, `*-prod-stage`) and cloud (`*-stage-cloud`). That doubles maintenance, and it creates two release owners per flavor. The two-owner problem is the only reason the version-slot and release-ownership plans exist.
**End result:** Each flavor has one release owner: a manually dispatched **cloud acceptance stage** (production-like, Farley-style) that creates the RC tag. Docker acceptance runs on every commit as a free, non-tagging gate, with separate workflows for the latest and legacy suites. QA and prod are one reusable workflow each (`_qa-stage.yml`, `_prod-stage.yml`) deploying to cloud. There is one tag series per flavor.

## Outcomes

- **Acceptance is two tracks (decided 2026-11-02, replaces "Docker commented out" for acceptance).**
  - **Docker acceptance, latest suite** (`<flavor>-acceptance-stage-docker-compose.yml`): runs on every prerelease run, against the commit-stage `sha-*` images on the runner. It is a gate only, and creates **no** tag. Free and fast, so red commits never reach cloud.
  - **Docker acceptance, legacy suite** (`<flavor>-acceptance-stage-docker-compose-legacy.yml`): a **separate** workflow from latest, so real projects can delete legacy by deleting one caller file and its pipeline job. Gate only, no tag. Legacy never runs on cloud (no extra Neon DBs or Cloud Run services; resolves Inventory Surprise 4).
  - **Cloud acceptance, latest suite only** (`<flavor>-acceptance-stage.yml`): the real acceptance stage in a production-like environment. **It owns the RC tag** (`<flavor>-v<x.y.z>-rc.N`). Trigger is **manual `workflow_dispatch` only**, run on a Docker-green commit; a `schedule:` cron sits in the file **commented out** for anyone who wants it automatic. QA consumes only cloud-created RCs.
  - Both Docker callers share one reusable `_acceptance-stage-docker-compose.yml` (input `suite-set: latest|legacy`); cloud callers use `_acceptance-stage.yml`.
  - **Naming (confirmed 2026-11-03, legacy suffix order `-docker-compose-legacy`):** Docker workflows carry a `-docker-compose` suffix; cloud has **no** suffix, because cloud is the real acceptance stage. So today's `<flavor>-acceptance-stage.yml` (Docker) becomes `-docker-compose`, today's `-acceptance-stage-legacy.yml` becomes `-docker-compose-legacy`, and today's `-acceptance-stage-cloud.yml` becomes the bare `<flavor>-acceptance-stage.yml`. This invalidates Inventory Surprise 10's "no pipeline edit": `_prerelease-pipeline.yml` (`:401`, `:440`) must dispatch the `-docker-compose[-legacy]` names, per flavor during rollout. README badges that point at `<flavor>-acceptance-stage.yml` will show cloud runs after the rename.
- **QA and prod: one workflow per stage per flavor.** Each is a thin caller of `_qa-stage.yml` / `_prod-stage.yml`, cloud active, with the Docker deploy and wait steps commented out next to them (unchanged decision for QA/prod). The `*-{qa,prod}-stage-cloud.yml` files are gone.
- **Consequence: the automatic chain stops at the Docker gates.** Because RCs only appear when cloud acceptance is dispatched, `_prerelease-pipeline.yml` no longer auto-runs QA after acceptance, its "Fail If No RC Tag On SHA" check (`:419`) moves to the cloud stage, and `_meta-prerelease-pipeline.yml`'s `tag-meta-rc` / flavor RC manifest waits on manually created RCs. Accepted 2026-11-02 for cost control.
- **One release owner per flavor.** There are no `*-cloud-v*` tags. Version bumps, prerelease probes, `drift` and `cross-lang-system-verification` work unchanged on the single tag series.
- **The docs are honest about what Docker means.** If someone uncomments Docker, acceptance runs in a real environment that is thrown away after the run, while QA and prod are only a zero-cost stand-in with nothing persistent. The comment and the docs both say so.
- **Cloud is $0 in normal use, with a hard stop.** Cloud acceptance is manual-only (cron commented out), and in practice costs ~$0 per run anyway because Cloud Run bills only while handling requests (180k vCPU-s/month free). QA and prod are manual. Manual `workflow_dispatch` is always available. Cloud Run deploys the public GHCR images directly, so nothing is stored in Artifact Registry. A billing kill-switch disables project billing at about €1. Normal use costs $0, and the worst case is a few cents, because GCP budget data lags before the kill-switch fires. Strictly guaranteed $0 isn't possible on GCP; Docker acceptance is the always-free path. (Decided 2026-11-02: option 1, as close to $0 as possible on GCP.)
- **Replaces the old plans.** `20261031-2111-move-release-ownership-to-cloud` is absorbed here, and `20261031-2109-cloud-prod-component-version-slots` (incident fix already landed) is closed. Both were deleted when this plan was added.

2. **Cloud acceptance has no `sonar` job**, but Docker does (`multitier-java-acceptance-stage.yml:345-379`). Keep it, since it doesn't depend on the deploy target.
3. **Only multitier-java uses `_deploy-stage-cloud.yml`.** The other 10 cloud QA and prod files (`{monolith-*,multitier-dotnet,multitier-typescript}-{qa,prod}-stage-cloud.yml`, 184–339 lines each) follow an older inline model: `google-github-actions/deploy-cloudrun` straight from GHCR, services named `<flavor>-qa` and `external-real-production`, a `DATABASE_URL=db-connection-string` secret, no Keycloak, no migrations and no smoke tests. 4. **Legacy and latest acceptance run in parallel.** `_prerelease-pipeline.yml:389` and `:430` start them as parallel jobs. On Docker each run gets its own runner.
